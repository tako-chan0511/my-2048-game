# ゲームエンジンの契約（STEP 6）

## 型と責務

- `BoardSize`：3〜10の整数を表す型。実行時も範囲と整数を検証。
- `Direction`：`up / right / down / left`。
- `Tile`：一意な`id`と整数の`power`。実際の値は`1n << BigInt(power)`。
- `Board`：行優先のN²要素。空きは`null`。ID重複・疎配列を拒否。
- `RngState`：アルゴリズム識別子とuint32内部状態。シード0も有効。
- `GameSettings`：サイズ、目標、初期枚数、4の確率、Undo上限、モード。既定は4×4・2048・2枚・4が10%・normal。サイズ・目標・枚数・確率はUIで変更可能。Undo上限の既定値は10で、Undo使用数はセッションで管理。
- `Position`：盤面、`bigint`スコア、有効手数、乱数状態、次のタイルID。Undoではこの単位を復元する。
- `GameState`：ルール版、初期シード、適用設定、Position、過去最大指数、更新番号。

設定は3〜10のサイズを許可し、初期タイル数がそのサイズの全マス数を超える場合や、不正なモード・制限値は明示的に拒否します。GameState検証時には盤面の要素数と適用設定のサイズも照合します。スコアは非負のbigint、手数・ID・更新番号は安全な整数です。壊れた指数や際限ないBigInt生成を避けるため指数の上限を128とし、超過は例外で通知します。本実装の最大100マス・出現数字2/4の理論上限も指数101以下なので、通常のプレイで指数128に到達することはありません。

## スライドと合体

1. 移動方向の端から順に各行・列の元タイルを取り出す。
2. 空きを除き、元の隣接する同指数2枚を1枚へまとめる。
3. 元タイルを2枚ずつ消費し、出力タイルを再び入力にはしない。
4. 生成した値をbigintスコアへ加え、空きで埋める。
5. 合体後の盤面が変化した場合だけ新規タイルを1枚生成し、手数を1増やす。

`slideLine`と`slideBoard`は新規タイルを生成しません。従って合計値が保存されます。`moveGame`だけがスライドと出現を統合し、増加する合計値は出現タイルの値と一致します。アニメーション拡張に備えて移動元・移動先・合体元IDを結果に含めています。

入力を変更せず、新しい状態は凍結して返します。変化しない移動では元のGameStateをそのまま返し、スコア・手数・ID・更新番号・乱数を一切進めません。ゲームオーバー状態でも同様です。

## 乱数プロトコル

- バージョン：`mulberry32-v1`。uint32シード0〜4294967295。
- 乱数状態は引数と戻り値で明示し、`Math.random`、時刻、グローバル可変状態を使用しません。
- 出現時は行優先で空きマスを列挙し、空きインデックス→0〜99の数字抽選の順に消費します。
- 4の確率をpとすると抽選値が100-p未満なら2、それ以外は4です。既定p=10は従来通り0〜89が2、90〜99が4です。設定上の確率は整数0〜100で検証します。
- 空きが1マス、確率が0%・100%でも、それぞれの抽選を省略しません。
- 全マス使用済みの場合は抽選しません。
- 一様な整数抽選には棄却法を使用します。uint32の上端の余りを捨て、実際の消費回数を返します。異常な乱数ソースで無限ループにならないよう1抽選128回で例外とします。
- `getRandomState` / `restoreRandomState`で検証・コピーした内部状態を取得・復元できます。復元後は同じタイル位置・数字・IDを再現できます。
- UIで新規ゲームを開始するときのみ`crypto.getRandomValues`でシードを作ります。

乱数・走査順・合体ID発行順を変更する場合は版を更新する必要があります。ルール版は`2048-v1`です。固定シード0の初期盤面・乱数状態をテストで固定しています。

## 目標と終了

適用済み設定の目標数字（既定2048）以上に到達した最初の有効手で`justReachedTarget`を返します。過去最大指数を保持するためUndoしても達成状態を維持できます。達成は入力禁止にせず、通常モードはどの方向にも動けない場合だけゲームオーバーです。時間・手数制限はセッション層で終了判定します。目標達成とゲームオーバーは同時に成立できます。

## セッションと保存

`GameState`はSTEP 1〜3のゲームエンジンと互換です。`PlaySession`がGameState、Positionの履歴、Undo使用数、目標通知済み、終了通知の更新番号、ポップアップをまとめます。有効な移動だけ直前のPositionを記録し、UndoでPositionのみを戻します。`revision`はUndoでも進めるため、`revision = moveCount + 2 × undoUsed`が成立します。

通常のUndo上限では、残り回数分の直近履歴を保持します。無制限の場合は履歴を自動削除しません。時間切れはUndo不可、手詰まりと手数上限は履歴と回数があればUndo可能です。PlaySessionに開始・締切・最後に観測した時刻を保持し、各入力時に注入された現在時刻を使って判定します。表示のintervalは時刻を減算せず、保存した締切から残量を計算します。詳細は[モード仕様](modes.md)を参照してください。

保存とUIの接続はcomposable、保存形式とlocalStorage処理はservicesへ分離しました。スコアは10進文字列へ変換し、復元時に盤面・設定・手数・タイルID・スコア等の整合性を検証します。詳細は[保存・Undo仕様](persistence.md)を参照してください。

## テスト方法

要求された合体例、全方向の境界、合体ID、合計保存、乱数消費、予測可能な抽選境界、目標と詰みを検証します。独立したスタック方式の参照計算と固定入力64盤面×4方向を比較し、複数シードの160操作でも状態遷移を検証します。テストに時刻依存や確率的な成功判定はありません。


## 設定適用と開始直後の終了

設定値の型・範囲・整数・項目名は`validation.ts`に集約し、エンジンと設定UIが同じ検証を使用します。`settings.ts`は検証結果に到達不能や初期全マス配置の警告を追加します。警告をエラーや達成保証として扱いません。

`use2048Game`は編集中の`draftSettings`と`GameState.settings`を分け、`applySettings`が検証成功後に`createGame`で作成した結果だけを採用します。通常の`newGame`は適用済み設定を使います。新規ゲームの構築が失敗した場合は以前のGameStateとポップアップを保持します。

初期全マス配置が手詰まりなら、採用直後にゲームオーバーポップアップを開きます。スコアと手数は0のままです。設定・数学的警告の詳細は[設定仕様](settings.md)を参照してください。


## 表示層への移動結果（STEP 6）

`moveSessionWithResult(session, direction, nowMs)`は、従来のセッション更新と同時に、その1回の`moveGame`が返した`MoveResult`を返します。移動不能・ブロック中は`move: null`です。従来の`moveSession`はそのセッション部分を返す互換APIとして維持します。

スライド・合体・新規タイル抽選・得点計算の実装は変更しません。Vue側は`motions`、`merges`、`spawned`と移動前盤面を参照して演出し、結果の再計算はしません。この一時情報はゲーム状態、UndoのPosition、保存形式へ含めません。
